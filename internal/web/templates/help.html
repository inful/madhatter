Getting Started

The dashboard is your control center. It shows your status, next HAT day, next WFH day, and upcoming leave.

If your assignment was swapped, you will see the swap icon on your HAT tag and can hover for details.

Leave And WFH

Use Leave to report absences. Admins review and manage leave records from the management page.

If a colleague calls in sick, any authenticated user can register that absence on their behalf via the Someone Called In Sick form (link in the user menu under Leave). The date is pinned to today — the form re-validates against the server's clock, so a tampered submission cannot file a future or past-dated leave. The same cover-assignment and maintenance machinery runs as the regular report flow; the row is always recorded as plain Leave (no leave-type selector, no email address in the member picker). A duplicate row for the same person on the same day is refused rather than stacked. If the absence is expected to last longer than today, the colleague or an admin can extend it via Manage Leave.

Each leave record carries a leave type tag (Leave or Conference). Plain Leave is the default and behaves exactly as before. Conference leave is the same in every respect except for how it surfaces on the dashboard: the "Today" status badge changes from On leave to @conference, and the schedule-matrix cell swaps its plane icon for a people-group icon and uses a distinct colour. The tag is purely cosmetic — it does not change scheduling, cover assignment, or quotas.

Use WFH to submit work-from-home requests. Requests are settled by policy and may be approved or denied based on capacity rules.

If you need to report WFH for today due to unforeseen circumstances (e.g. you're sick and working from home), use the "WFH today" button on the dashboard. The request is created and settled inline so the dashboard reflects the outcome within the same request — no waiting for the next settlement tick. The button only renders when you're currently On-site, today is a business day, and the WFH feature is enabled. Capacity-floor enforcement is identical to the regular request path: if today's at-work count has already hit the floor, the report is denied rather than auto-approving through. A flash banner reports the outcome (approved / denied / error). The same path is exposed as POST /api/v1/wfh/report-today and the CLI subcommand wfh report <member-id>.

Approved WFH requests can be withdrawn by the requester (or by an admin) up until midnight of the WFH day.

How WFH Is Settled

Quota

Each member has a WFH quota per period: a cap on how many work-from-home days count against you. Both ad-hoc requests and contracted recurring weekdays are counted together. When your quota is full, the form blocks new requests until you withdraw an approved one to free a slot.

Periods are fixed-length windows aligned to a known Monday. They start and end on the same day-of-week for everyone, so quota usage is comparable across the team.

On-site coverage

Every day has a minimum number of people who must be physically on site. The minimum is the larger of two values: a percentage of active members, and a hard absolute floor. The percentage is rounded up before the comparison so a fractional result never under-counts. The system uses whichever is higher so a small team can never drop below the absolute floor even when the rounded percentage would otherwise allow it.

On a given day, members already on leave, members with a recurring weekday, and approved ad-hoc WFH requests all count against that day's on-site capacity. The remaining members are the pool of available WFH slots for that day.

When the day's at-work count has reached the floor, the WFH chip on the dashboard turns orange for that column to signal no more WFH can be approved that day. Any new pending request for that date will be denied at settlement time, because approving it would drop on-site coverage below the floor.

Settlement

Pending WFH requests are processed in a rolling window of one full quota period ahead (7 days by default), not all at once. The system reviews requests whose dates fall inside that window, decides them against the day's available slots, and leaves anything further out as pending until it enters the window. The scheduler runs every {{.WFHSettlementInterval}} so a request submitted during business hours is usually settled within the same quarter-hour.

When more members request WFH on the same day than there are slots, requests are prioritised by who has used the fewest WFH days in the current period. Ties are broken by who submitted first.

Recurring weekdays

If a member has a weekday set as recurring WFH, the system treats every upcoming occurrence of that weekday in the current period as an approved request. Those rows appear in the WFH list alongside ad-hoc requests, marked with the same Approved status, and the same Withdraw button works on them. Withdrawing a single occurrence frees one quota slot for that period; the next period reverts to the configured schedule.

If you self-withdraw a recurring occurrence and then re-request the same date, the new request is treated as ad-hoc (not recurring) and goes through normal settlement — so it may be denied if on-site coverage is at the floor. The recurring pattern for that weekday resumes from the next occurrence onward.

Withdrawing

Approved requests can be withdrawn by the requester or by an admin at any time before the WFH day itself. The day itself is still withdrawable, but once the day has passed the request is locked.

You can also cancel a pending request (before settlement) from your WFH list. In both cases, if you change your mind afterwards you can re-request the same date — the row is resurrected in place as a new pending request, audit fields are cleared, and it will go through settlement like any other pending request.

Admin withdrawals are different: they represent an admin's decision and cannot be reversed by re-requesting. If an admin withdraws your WFH, ask them to reinstate it if you want it back.

WFH Past-Period Purge

The wfh_requests table accumulates history forever by default, so a long-running deployment would grow without bound. To keep it bounded, the settlement scheduler hard-deletes rows whose date is strictly before the start of the previous quota period after each tick. The current and previous periods are always preserved.

Admins can preview or run the same purge from the web UI at /admin/wfh/purge (admin only). GET shows the cutoff and the row count that would be deleted; POST with confirm=true commits the deletion and redirects back with a flash banner. The web preview never mutates the table.

The same operation is exposed on the CLI as wfh purge (dry-run by default; pass --apply to commit, or --before YYYY-MM-DD to override the period-derived cutoff for a one-off catch-up clean). Errors with WFH feature is disabled when WFH_ENABLED=false. Set WFH_PURGE_ENABLED=false to opt out of the scheduler-driven cleanup without disabling the WFH feature as a whole.

HAT Day Swaps

Use Swaps to request exchanging your HAT day with another teammate.

Incoming requests can be accepted or rejected. Expired requests are automatically cleaned up and cannot be accepted.

You can cancel your own pending requests before they are accepted.

User Approval

New users who sign in via an OAuth provider (Google, GitLab, etc.) start in a pending state. They see a "your account is awaiting approval" page and cannot log in until an admin approves them. Pending users appear on the team page under "Awaiting Approval" with Approve and Deny buttons.

Admins are notified by email when a new user signs in. The email links to the team page where the admin can approve or deny.

Approved users become active. An admin can also deactivate an active user (e.g. when they leave the team). Deactivated users cannot log in but their team-member row is preserved for audit. They appear under "Deactivated Users" on the team page with a Reactivate button.

Deactivation and reactivation both work by toggling a flag on the user row. Sessions belonging to a deactivated user are rejected by ValidateSession on the next request, so changing the flag is effective immediately for any future request.

How HAT Days Are Assigned

Every business day on the rota gets exactly one HAT day — the person who carries the duty that day. Two independent rotations run side by side, so a leave on one day never reshuffles the rest of the rota.

The original-HAT rotation (R1)

Each business day is assigned to the next active member in alphabetical order, wrapping around at the end of the list. The R1 index is read from a small persisted state row that records the date of the most recent original assignment and the index that was used. So Alice, Bob, Carla, Dave, Alice, Bob, … is the pattern on a four-person team with no breaks.

Because the state persists in the database, a schedule that is generated in multiple calls — for example, a 14-day rolling window that runs on every page load, or a partial regeneration of a sub-range — picks up exactly where the previous call left off. There is no in-memory cursor to clobber, so a concurrent regeneration can't roll the rotation back.

The R1 state advances only when a new original assignment is successfully written. A failed write leaves the state untouched, so a retry picks up at the same index. Weekends and configured holidays are skipped — the index only advances on a day that becomes an assignment.

The cover rotation (R2)

When the R1 member is on leave, the system needs a cover. Covers come from a second rotation that is deliberately independent of R1: it advances on its own, not as a side effect of who's on leave, so a long leave on one person cannot freeze the cover slot on another.

The cover rotation is a small piece of persistent state — a single row in the database that remembers the last date an index was computed and the index for that date. The flow is:

  1. First call ever: the row doesn't exist, so the system seeds it at the current date with index 0 — i.e. the first member in the active list. The current date is its own anchor.
  2. Same date, later call: return the stored index directly, no advance.
  3. Later date: count the working days (weekdays that are not holidays) between the stored date and the new date, add that count to the stored index, take the result modulo the team size, persist the new state, and return it. A one-day advance shifts the index by one slot; a Monday-to-Friday advance of three working days shifts it by three.
  4. Earlier date: walk backward from the stored state without updating it. This is a safety net — the system only ever looks forward in normal operation, so this branch shouldn't fire.

Because the state stores the index for the date it was computed on (not just an opaque counter), retroactive changes to the holiday list only affect the gap between the last stored date and the current query, not the entire history of the rota.

Picking the actual cover

Whichever member sits at the R2 index becomes the primary candidate for cover. If that person is also on leave for the same day, the system advances cyclically through the member list and picks the first one who is not. So covers never collide with active leave records.

What this guarantees

  • The R1 (original) and R2 (cover) for any given date are both fully determined by the team composition and the date — there is no randomisation and no dependence on the order in which leaves were reported or the order in which the schedule was generated.
  • The same person cannot be picked for every new leave (the old failure mode this algorithm replaced).
  • Across a year of random leave, the total HAT-day count — originals plus covers — comes out close to equal for every team member, with a measured spread of 1–6 days on a 5-person team over 250 working days.
  • Existing schedule entries are preserved: a leave that gets added after the rota is already generated only triggers a cover for the affected dates, never a regeneration. A regeneration of a sub-range reuses the persisted state, so the rotation continues from where the surrounding schedule left off instead of restarting from the first member.

Periodic reassignment (ReassignCovers)

The server runs the cover-assignment algorithm against every leave on startup (and the reassign-covers CLI command re-runs it on demand). The reassignment uses a separate rotation anchor from the one used for ad-hoc new-leave submissions, so a periodic reassign never disturbs the rotation position of leaves submitted through the web form or API between runs.

The reassign anchor records the end of the most recent reassign run. On unchanged data it lands on the same date and slot on every run, which is what makes the operation idempotent on stable data. If a new leave is added between runs, the next reassign reprocesses from scratch and the new leave's slot is consumed by the rotation as expected.
